# 学習した AI の設計メモ（2026-10-06）

手書きの CPU（よわい〜さいきょう、cpu.js）とは別に、自己対局で学習したニューラルネットで打つ「AI」を作るための設計。
コードはまだ書いていない。ディレクターとオーナーが読んで、末尾の「決めてほしいこと」に答えたら作り始める。

## 0. 要約

- **方式**: 価値ネット V（公開の情報から見た「各プレイヤーの勝つ見込み」）を学習し、
  **買う・獲得する判断は「買ったあとの状態」を作って V で比べる**（TD-Gammon 型。探索なし、または 1 手だけ）。
  ほかの判断（アクションの順、各種の問い）は最初はさいきょう CPU の手書きのまま。段階を追ってネットに移す。
- **教師**: 最初はさいきょう同士の棋譜で V を学習し、そのあと自己対局で強くする。
- **HAKUSAN**: 自己対局は Node で engine.js・cards-*.js をそのまま動かす（移植しない）。学習は Python・PyTorch の CPU 版で足りる（GPU は要らない）。
  1 ノード（256 コア）の 1 ジョブで「自己対局 → 学習 → 測る」を何世代か回す。全部で 1 ノード × 1〜2 日の見込み。
- **ブラウザ**: ネットは約 15 万パラメータ。重みは 300 KB 前後の 1 ファイル、推論は手書きの JS（約 100 行）。外部ライブラリなし、sw.js でオフラインで動く。
  1 手の時間はスマホで数 ms。
- **画面**: 席の選択を「人／CPU（4 段階）／AI」にする。通信対戦ではホストの端末が AI を動かす。
- **合格の線**: AI 対 さいきょう、2 人・全拡張のランダムな王国、400 局（先手を交互）で勝率 60% 以上。

## 1. 何を学習するか

### 人数

- 学習は 2 人対戦だけ。エンジンは 2〜5 人のまま変えない。
- ネットの出力は人数ぶんの値（自分から席順に並べた各プレイヤーの「1 位になる見込み」、softmax で合計 1）。
  最初のモデルは 2 人ぶんだけ出す。3 人以上はモデルを足すとき（または同じ形の出力を増やして学習し直すとき）に扱う。カルカソンヌの決まり（DECISIONS 2026-09-30）と同じ形。

### ネットに任せる判断と、任せない判断

エンジンの判断は 2 つの入口から来る（cpu.js と同じ）。

- `nextMove(game)`: 手番の人がすること（アクションを使う／購入フェイズへ／財宝を出す／財源を使う／買う／イベント／夜 …）
- `answer(game, q)`: 効果の問い（`hand` / `supply` / `cards` / `choose`）。`purpose` は日本語の文で、種類が数百ある

ドミニオンの強さの大半は「何を何枚買うか」（デッキの中身）で決まる。そこで段階を分ける。

| 判断 | 段階 1・2 | 段階 3 以降 |
|---|---|---|
| 買う（王国・基本・イベント・何も買わない） | **ネット**（買ったあとの状態を V で比べる） | ネット |
| 財源を使って買う | **ネット**（「財源 n を使って X を買う」も候補に入れる） | ネット |
| 効果での獲得（`supply` の問いで、自分が獲得するもの） | **ネット**（同じく獲得したあとの状態で比べる） | ネット |
| 廃棄する札の選択（`hand`/`cards` で廃棄） | さいきょうの手書き | **ネット**（廃棄したあとのデッキの中身で比べる。1 枚ずつ選び、「やめる」も候補） |
| アクションを使う順・購入フェイズへ移る時 | さいきょうの手書き（`actionOrder`） | **ネット＋浅い試し打ち**（下の注） |
| 財宝を出す・夜・村人 | 手書き（今のまま） | 手書き |
| そのほかの問い（捨てる、山札の上に置く、`choose`、相手に何かさせる） | 手書き | 手書きのまま。困った場面が見つかったら個別に足す |

- 「買ったあとの状態」は、エンジンを動かさずに特徴量の上で作る（自分のデッキの中身に X を 1 枚足す、サプライを 1 減らす、残りのお金・購入数を減らす）。
  「買ったとき〜」の効果やイベントの効果は、この計算では表せないので、**候補そのもの（何を買ったか）も入力に入れる**。ネットはそれらの効果の値打ちも学べる。
  つまり実際には Q(状態, 候補) を、状態の特徴と候補の札の埋め込みから出す形になる。
- 自分が獲得する問いかどうかは、cpu.js の `wantedDirection`（`purpose` の文から読む）をそのまま使う。読めない問いは手書きに回す。
- 注（段階 3 のアクションの順）: 候補ごとに「この札を使ってから手番の終わりまで手書きで打つ」を数回試し、終わった状態を V で比べる。
  試すときは隠れた札（相手の手札と山札、自分の山札の順）を混ぜ直してから打つ（下の 2 節）。
  **今の game は持続の効果（`p.nextTurn` に関数）が残っていると `structuredClone` できない**（Node で確かめた。ランダムな王国の判断の場面の約 7%）。
  その場面では手書きに任せるか、actions.js の `replay`（控えから打ち直す）で作り直す。段階 3 の始めに決める。

## 2. 入力の表し方

### 隠れた情報を使わない（DECISIONS の決まり）

- 特徴量は **`viewFor(game, 自分の席)` から作る関数 1 つだけ**を通す。他の人の手札・山札はそこで枚数だけになっている。
- 自分の山札は viewFor では並びのまま残るが、**中身の枚数だけ数え、並びは使わない**（山札の上に置いた札を本人が知っている場合だけ別に数える）。
- 相手のデッキの中身（手札・山札・捨て札を合わせた札の種類と枚数）は、獲得・廃棄がすべて公開されるので記録から数えられる値として使う（今の CPU も相手の点を数えている）。
  伏せて置くマット（島など、`PUBLIC_MATS` 以外）は枚数だけ。
- 試し打ち（段階 3）の前には、隠れた札を混ぜ直す（相手は手札＋山札を混ぜて配り直し、自分は山札を混ぜる）。
- 確かめるテストを足す: 隠れた札だけを入れ替えた 2 つの game から作った特徴量が、ぴったり同じになること。

### 500 種のカード

カード（王国 498 種、基本・ランドスケープ・サプライ外を合わせて 852 種）は、次の 2 つを足したベクトル（32 次元）で表す。

1. **カードの性質の特徴量**（約 40 次元を線形に 32 次元へ）: コスト（金・ポーション・借金）、種類（アクション・財宝・勝利点・アタック・持続・リアクション・夜 …）、
   cpu.js の `feats` が文から読む +カード・+アクション・+購入・+金・廃棄・獲得・呪い、勝利点の数、財宝の額。
2. **カード ID の埋め込み**（学習する 32 次元、はじめは 0）。

- 学習中はときどき ID の埋め込みを 0 にして（10% 程度）、性質だけでも打てるようにする。後から足したカードや、学習でほとんど出なかったカードは性質だけで扱う。
- モデルのファイルに「ID の並び」を入れ、知らない ID は 0（性質だけ）にする。カードを足してもモデルが壊れない。

### 毎回違う王国

10 種の王国とランドスケープは、**集合として**扱う（並びに意味がない）。

- サプライ: 各山の（カードの埋め込み、残り枚数、今のコスト）を小さな MLP に通して足し合わせる（Deep Sets）。
- 自分のデッキの中身、自分の手札、場、相手のデッキの中身、廃棄置き場: それぞれ「枚数 × カードの埋め込み」を足し合わせる（枚数の多いものは log で抑える）。
- 数値: 手番の数、各人の点と点差、空の山の数、属州（植民地）の残り、山札・捨て札の枚数、財源・村人・借金・勝利点トークン、今の残りのお金・購入数・アクション数。
- これらをつないで MLP（256 → 256）→ 人数ぶんの値。候補の札の埋め込みも入れる（上の Q の形）。
- 集合の中の組み合わせ（村＋鍛冶屋など）は、足し合わせた後の MLP で拾う。足りなければ段階 2 の途中で、サプライに小さな注意（attention）を 1 層足す。

パラメータは合わせて約 15 万（埋め込み 852×32 ≈ 2.7 万、MLP ≈ 12 万）。

## 3. 学習の方法

### 候補の比べ

| 方式 | よいところ | 困るところ |
|---|---|---|
| **A. 価値ネット＋買ったあとの状態の比較（TD-Gammon 型）** | ネットが 1 つで単純。推論が軽い。エンジンを複製しなくてよい。ドミニオンの要の「買う」に直接効く | アクションの順などは別の手当てが要る（段階 3） |
| B. 方策＋価値ネット、PPO などの方策勾配 | すべての判断を同じ形で学べる | `purpose` が数百種の問いを同じ出力の形にそろえるのが大仕事。学習が不安定になりやすく、調整が多い |
| C. AlphaZero 型（MCTS＋方策・価値） | 探索で強くなる余地が大きい | 山札を混ぜる偶然と隠れた情報で、探索を決定化しなければならない。ジェネレータの途中で game を分けられず、持続が残ると複製もできない。計算は A の 100 倍規模、スマホの 1 手も重い |

**A を推す。** 理由: 強さの大半を占める「買う」をまっすぐ学べ、エンジン（ジェネレータ・複製できない場面）の制約に当たらず、
HAKUSAN の計算も、ブラウザの重さも小さい。足りなければ段階 3 で浅い試し打ちを足す（C の一部を後から借りる）。B は問いの扱いが重く、得るものに比べて手間が大きい。

### 学びかた

1. **さいきょうの棋譜で始める**: さいきょう同士（と さいきょう 対 つよい）を 10 万局打たせ、判断の場面ごとの状態と最後の結果（勝ち・負け・引き分け）を記録し、V を回帰で学ぶ。
   あわせて、さいきょうが選んだ候補の Q が一番高くなるよう順位の損失も少し入れる（はじめの手を さいきょう に近づけるため）。
   これで「さいきょう とほぼ互角」まで来る見込み。来なければ入力か形を直す（自己対局に進まない）。
2. **自己対局で強くする**: 今のモデル同士で打ち、最後の結果を目標に V を学び直す（モンテカルロの目標。必要なら TD(λ) に替える）。
   探るため、候補は Q の softmax（温度を世代ごとに下げる）で選び、序盤の数手は少し広めに選ぶ。
   相手は 8 割を今のモデル、1 割を過去の世代、1 割を さいきょう にして、自分の癖だけに強くなるのを防ぐ。
3. 世代ごとに前の世代と さいきょう に 400 局ずつ打たせ、前の世代に 55% 以上勝ったら新しいモデルにする。

## 4. HAKUSAN での回し方

### 分け方

- **自己対局（Node）**: engine.js・cards-*.js・cpu.js を**そのまま**使う。移植しない（500 種の効果を別の言語で書き直すと食い違いが必ず出る）。
  ネットの推論はブラウザと同じ手書きの JS（`ai/net.js`）を使うので、HAKUSAN と画面で打ち方が変わらない。
  特徴量も JS（`ai/features.js`）で作り、数値の列としてファイルに書く。Python は特徴量を作り直さない。
- **学習（Python・PyTorch）**: 特徴量の列を読んで学び、重みを書き出す（`train/train.py`、`train/export.py`）。モデルが小さいので **CPU 版の PyTorch で足りる**。GPU があっても使わなくてよい。
- 準備（オーナーが 1 回だけ）: Node の公式の Linux 版（tar.xz）をホームに展開して PATH に足す（root は要らない）。
  PyTorch は `pip install --user --break-system-packages torch --index-url https://download.pytorch.org/whl/cpu`（展開図の研究の README と同じく venv は使えない前提）。

### ジョブの形

展開図の研究と同じく `SINGLE` で 1 ノード 256 コアを使う。1 本のジョブで世代を回す。

```sh
sbatch jobs/job_ai.sh <名前> <始める世代> <世代数>   # 例: sbatch jobs/job_ai.sh base1 0 30
```

- 中では世代ごとに: ① `xargs -P 256` で Node の自己対局を 256 本 → ② Python で学習 → ③ Node で 400 局の測定 → `runs/<名前>/log.tsv` に 1 行（世代、サンプル数、対 前の世代、対 さいきょう、かかった時間）。
- 重みは `runs/<名前>/gen_<n>.bin`。止まったら、最後の世代から同じコマンドで続ける。
- 段階 0 に、局数と時間を測るだけの短いジョブ（`DEF -n 64`、数分）を入れる。下の見積もりはそれで直す。
- ジョブの投入はオーナーが手で行う。オーナーは `log.tsv` の末尾を貼り、最後の重みを scp で持ち帰る。こちらはそれを `ai/model.bin` に入れて測る。

### 計算量の見積もり

手元（Mac）で測った値: ルールの CPU どうし 2 人・全拡張のランダムな王国で **約 90 局／秒／コア**。さいきょう同士は **約 11 秒／局**（始めの型選びの自己対局が大半）。
HAKUSAN の 1 コアを手元の半分の速さと仮定する。

| 作業 | 量 | 1 ノード（256 コア）での時間 |
|---|---|---|
| さいきょうの棋譜 | 10 万局（約 20 秒／局） | 約 2〜3 時間 |
| 自己対局（ネットで打つ） | 1 世代 20 万局（ネットの推論込みで 5〜10 局／秒／コア） | 約 2〜4 分 |
| 学習 | 1 世代 約 1,000 万サンプル × 2 回 | 約 5 分（CPU の PyTorch、10 万サンプル／秒と仮定） |
| 測る | 400 局 × 2（相手が さいきょう の局は約 10 秒） | 1 分弱 |
| **1 世代** | | **約 10 分** |

- 段階 1（基本だけ）: 棋譜 1 時間＋30 世代 ≈ **半日弱のジョブ 1 本**。
- 段階 2（全拡張）: 棋譜 3 時間＋100 世代 ≈ **20 時間前後（2〜3 本に分ける）**。
- 合わせて **1 ノード × 1〜2 日**。推定は段階 0 の計測で直す（ずれは数倍まであり得る）。

## 5. ブラウザでの動かし方

| 方法 | 重さ | 決まりとの関係 |
|---|---|---|
| ONNX Runtime Web | wasm 込みで数 MB〜10 MB | 外のスクリプトは決まったホストからしか読めない（RULES §1）ので、自分で置くことになる。重い |
| TensorFlow.js | 1〜3 MB | 同上 |
| **手書きの推論（JS）** | 推論 約 100 行＋重み 300 KB | ライブラリなし。モデルは行列の積と ReLU だけなので足りる |

**手書きを推す。**

- 重みは float16 の 1 ファイル（`ai/model.bin`、約 300 KB）と、形・ID の並び・版を書いた `ai/model.json`。読み込んだら Float32Array に直す。
- sw.js の SHELL に `ai/net.js`・`ai/features.js`・`ai/player.js`・`ai/model.bin`・`ai/model.json` を足す（オフラインで AI と遊べる）。
- 1 手の時間: 1 回の推論は約 15 万回の掛け算で、スマホでも 1 ms 未満。買う判断は候補 15 前後なので数 ms。段階 3 の試し打ちを入れても 100 ms 以内を目安にする。
  画面を止めないよう、さいきょうの型選び（planner.js）と同じく Web Worker で動かす。
- さいきょう は対局の始めに型選びで数秒考えるが、AI はその待ちがない。

## 6. 画面

- 席の選択を **人 ／ CPU（よわい・ふつう・つよい・さいきょう）／ AI** にする。AI は CPU の段階の 1 つではなく、別の種類の席 `{ type: 'ai' }` にする（オーナーの「CPU と AI は別物」）。
  表示は「AI」。
- 戦績（main.js の「CPU（○○）に x勝y敗」）に「AI に x勝y敗」を足す。保存の形に新しい項目が増えるだけで、古い記録はそのまま読める。
  席を覚える保存（`isValidSeat`）に `ai` を足す。古い版の保存データは今までどおり読める。
- 3 人以上のときの AI は、段階 1・2 では選べないようにする（「AI は 2 人のときだけ」と出す）。→ 決めてほしいこと 1
- 通信対戦（online.js）: CPU の席と同じく、**ホストの端末が AI の手を決めて当てる**。ゲストはモデルを読まない。待合の席の選択にも「AI」を出す。
  注意: 古い版のゲストは席の `type: 'ai'` を知らない（main.js の `seatName` が CPU の段階を探して落ちる）。名前の引き方を落ちない形に直してから出す。
  切れた人の代打は今までどおり CPU（ふつう）。

## 7. 強さの測り方と合格の線

- 測るのは HAKUSAN（と手元の数十局の確認）。先手を交互にし、引き分けは 0.5 勝。王国は毎局ランダム（同じ種の列を新旧で共有して比べる）。
- 400 局なら勝率のぶれ（標準誤差）は約 2.5%。60% は 50% から約 4 倍離れているので、偶然では出ない。

| 段階 | 合格の線 |
|---|---|
| 0 | 仕組みが回る。棋譜だけで学んだ AI が ふつう に 90% 以上 |
| 1（基本だけ） | AI 対 さいきょう、基本の王国 400 局で 60% 以上 |
| 2（全拡張） | AI 対 さいきょう、全拡張のランダムな王国 400 局で **60% 以上**（これが「最強」の合格） |
| 3（アクションの順・廃棄） | 段階 2 のモデルに 55% 以上、スマホで 1 手 100 ms 以内 |

## 8. 段階分け

| 段階 | やること | 終わりの条件 |
|---|---|---|
| 0 | `ai/features.js`・`ai/net.js`（推論）・Node の自己対局と記録・Python の学習と書き出し。手元で小さく 1 周（数百局）。隠れた情報のテスト。HAKUSAN の計測ジョブ | 手元で 1 周が通る。JS と PyTorch の推論が同じ値（差 1e-4 以下）。計測ジョブの値で見積もりを直す |
| 1 | 基本の 26 種だけで、棋譜 → 自己対局 30 世代 | 対 さいきょう（基本）60% |
| 2 | 全拡張。ランドスケープ・ポーション・借金・財源の候補も扱う | 対 さいきょう（全拡張）60% |
| 2.5 | 画面に「AI」の席、Worker、SW、戦績、通信対戦のホスト | `npm run audit:browser -- deck-builder` が通る。オーナーが遊んで確かめる |
| 3 | 廃棄の選択、アクションの順（試し打ち） | 段階 2 のモデルに 55%、スマホで 100 ms 以内 |
| 4（あれば） | 3 人以上（出力を人数ぶんに増やして学習） | オーナーが決める |

段階 2.5 は段階 1 の後に先に入れてもよい（基本の AI で画面を先に確かめられる）。

## 9. 決めてほしいこと（オーナー）

### 特徴量（次元）

- カードの性質 P = 35（種類 20 + コスト・ポーション・借金・点・財宝の額・+カード・+アクション・+購入・+金・引くまで・廃棄・呪い・獲得・終点）。名前の並びは `PROP_NAMES`。
- 袋（枚数の集合）5 つ: `BAGS` = 自分のデッキ全体・自分の手札・自分の場・相手のデッキ全体（台帳）・廃棄置き場。重みは log(1+枚数)。
- サプライ: 山（と、あれば場のランドスケープ）ごとに ID・残り/10・コスト/10・禁輸の印/3・勝利点トークン/10。
- 数値 NS = 32（`SCALARS` の順。手番数・点・点差・空の山・属州・終盤度・枚数・財源・村人・借金・勝利点トークン・今のお金・購入・アクション …）。
- 相手は次の席 1 人だけ（2 人対戦）。相手のデッキは、`startLedger` が対局の始めに作る台帳（獲得・廃棄の公開の記録）から数える。台帳がなければ見えている札（捨て札・場・伏せないマット）だけ。
  台帳は札が山に戻る・席の間で渡る効果（大使など）を数えない。
- **隠れた情報**: `encode` は手札・山札を `{length}` にした `publicView`（viewFor と同じ隠し方。viewFor は持続の効果が残る場面で structuredClone に失敗するので、浅く写す自前のもの）の上で作る。
  相手の手札・山札（中身も順も）、伏せたマット、自分の山札の並びを入れ替えても同じ値になることを test/ai.mjs が毎判断で見る（viewFor を通した game からも同じになることも）。

### 候補（`cand`）

`{ kind, pile, id, cost, coffers }`。`kind`: 0 買う・1 効果で獲得・2 イベント等を買う・3 何もしない。`pile` は山の ID（買う・獲得に渡す名前）、`id` は山の一番上の札。
`coffers` > 0 は「財源を n 使ってから買う」（買えないものを財源で届くときだけ。必要な最小の n）。呪いは候補に入れない。
自分の判断のうち、買う（購入が残り、財宝を出し終えたとき）と、自分が獲得する supply の問い（`wantedDirection` が `best`）だけが候補つき。

**選んだあとの状態**（`postState`）: kind が 0・1 のとき、自分のデッキの袋に `id` を 1 枚足し、サプライの同じ山の残りを 1 減らす。ほかの変化は候補の値（`candExt` = コスト/10・使う財源/8・点/10・属州か植民地か）から学ぶ。

### モデルの形（model.json）と推論

- D = 32、隠れ層 H = 256、出力 2（自分・相手の勝つ見込み。softmax）。パラメータ 163,778（emb 853×32 = 27,296、W1 は 256×264、W2 は 256×256 など。入力 264 = 5×32+32+32+32+4+4）。
- 重みは `shapes` の順（emb, Wp, bp, Ws, bs, W1, b1, W2, b2, W3, b3）に float16 で並ぶ。Linear は `[出, 入]`（PyTorch の `nn.Linear.weight` と同じ並び）。
- カードのベクトル = `Wp·性質 + bp + emb[ID の番号]`（番号 0 = 並びにない札は埋め込みなし）。ID の番号は model.json の `ids`（1 から）。
- 入力 x = [袋 5 つ（各 D）; サプライ（D）; 数値（NS）; 候補のベクトル（D）; 候補の種類 one-hot（4）; candExt（4）]。サプライ = Σ relu(Ws·[カードのベクトル; 山の値 4] + bs)。
- 出力 = softmax(W3·relu(W2·relu(W1·x + b1) + b2) + b3)。候補の値打ち = 出力の 0 番目（自分が勝つ見込み）。

### 記録の形（`train/selfplay.mjs`）

```sh
node train/selfplay.mjs --games 20 --mode expert|ai --out runs/x/shard0 [--seed 1] [--model ai/model] [--temp 0.05] [--base]
```

`<out>.json`（`arrays` に名前・型・長さ・バイト位置）と `<out>.bin`（配列を順に並べただけ。リトルエンディアン）。Python は `np.fromfile(bin, dtype, count=length, offset=offset)` で読む。
`mode=expert` は さいきょう同士（棋譜）、`mode=ai` は AI（席は局ごとに交代）対 さいきょう。どちらも両方の席の判断を記録する。1 ファイル = 1 プロセス = 1 シャード。

判断 D 個・候補 C 個・局 G 個・ID の数 V（= len(ids)+1）。NS = 32、P = 35。

| 配列 | 型 | 長さ | 中身 |
|---|---|---|---|
| `decGame` | int32 | D | 判断が属する局の番号（0 から。打ち切りの局は除いて詰める） |
| `decSeat` | int8 | D | 判断した席（特徴量はこの席から見たもの） |
| `decSource` | int8 | D | 0 さいきょう・1 AI |
| `decChosen` | int16 | D | 選んだ候補の番号（その判断の中での） |
| `scalars` | float32 | D×NS | 数値 |
| `bagOff` | int32 | D×5+1 | 判断 d・袋 b の中身は `bagIdx[bagOff[d*5+b] : bagOff[d*5+b+1]]`（最後に番兵） |
| `bagIdx`・`bagCnt` | int16 | 合計 | 袋の札の ID の番号（0 = 並びにない）と枚数。重みは log(1+枚数) |
| `supOff` | int32 | D+1 | 判断 d のサプライは `supIdx[supOff[d] : supOff[d+1]]` |
| `supIdx` | int16 | 合計 | 山の一番上の札の ID の番号 |
| `supExt` | float32 | 合計×4 | 残り/10・コスト/10・禁輸/3・勝利点トークン/10 |
| `candOff` | int32 | D+1 | 判断 d の候補は `[candOff[d], candOff[d+1])` |
| `candKind` | int8 | C | 0 買う・1 獲得・2 イベント・3 何もしない |
| `candIdx` | int16 | C | 候補の札（イベントはそのイベント）の ID の番号。3 は 0 |
| `candExt` | float32 | C×4 | コスト/10・使う財源/8・点/10・属州か植民地か |
| `gameResult` | float32 | G×2 | 席ごとの結果（勝ち 1・引き分け 0.5・負け 0） |
| `gameTurns` | int16 | G | 席 0 の手番数 |
| `gameSeatAI` | int8 | G | AI の席（expert モードは -1） |
| `cardProps` | float32 | V×P | ID の番号ごとのカードの性質（行 0 は 0） |

- 学習の目標: 判断 d の目標 = `gameResult[decGame[d]][decSeat[d]]`。損失は、選んだ候補の「自分の勝つ見込み」への回帰（`decSource=0` の棋譜では、選んだ候補の値が一番高くなる順位の損失も）。
- **選んだあとの状態を Python で作る規則**（`postState` と同じ）: 候補 kind が 0 か 1 のとき、判断の袋 0（自分のデッキ）の `candIdx` の枚数を +1（なければ足す）、サプライの `supIdx == candIdx` の山の残り（`supExt[:, 0]`）を −0.1。kind 2・3 は変えない。そのうえで候補のベクトル・種類・candExt を入力に足す。
- 台帳（相手のデッキ）は袋 3 に入っている。Python は特徴量を作り直さない。
- 判断が少ない局もあるので、サンプルの重みは判断ごとに等しくしてよいし、局ごとに等しくしてもよい（0-B で決める）。

### 実測（手元の Mac、全拡張のランダムな王国・ランドスケープ 0〜2 枚）

- 記録 1 局: さいきょう同士 約 7 秒、AI（乱数の重み）対 さいきょう 約 7〜9 秒（時間の大半は さいきょう の型選び）。AI 同士は 1 局 約 0.5 秒（net の推論は 1 判断 約 5 ms）。

- 20 局（4 プロセスで 5 局ずつ）: 約 47 秒。判断 1,366、候補 15,450。
